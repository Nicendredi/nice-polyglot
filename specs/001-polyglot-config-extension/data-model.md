# Data Model: Nice Polyglot — Multilingual Configuration Extension

**Branch**: `001-polyglot-config-extension` | **Date**: 2026-04-25

---

## Entities

### LanguageCode

A short ISO 639-1 two-letter string identifying a language.

| Attribute | Type | Rules |
|---|---|---|
| `code` | `string` | Two lowercase letters (e.g., `en`, `fr`, `es`). Unrecognized codes are treated as invalid. |

**Special rule**: `en` (English) is always valid and is the fallback for every category. It cannot
be removed from the effective accepted set.

---

### LanguageCategory

One of 8 configurable output or interaction types whose language can be set independently.

| Identifier | Description | Constrained by `accepted_languages`? |
|---|---|---|
| `interactions` | Agent-to-user conversational language | No — may use any language |
| `artifacts` | SpecKit artifacts (spec.md, plan.md, tasks.md) | Yes |
| `documentation` | User-facing documentation generated by agents | Yes |
| `code` | Generated source code | Yes |
| `code-comments` | Comments inside generated code | Yes |
| `log-messages` | Log output messages generated by agents | Yes |
| `internal-docs` | Internal/developer-facing documentation | Yes |
| `commit-messages` | Git commit messages generated by agents | Yes |

**`interactions` is a special category**: it is the only conversational category and its language
is not constrained by `accepted_languages`. A contributor may interact in Spanish even if the
project only accepts English and French for shared files (FR-008).

---

### ConfigLayer

A single YAML file contributing settings to the effective language policy. Three instances exist,
applied in ascending precedence order.

| Layer | Path (relative to `.specify` root) | Precedence | Who controls it |
|---|---|---|---|
| Base | `extensions/nice-polyglot/nice-polyglot-config.yml` | Lowest (1) | Extension author |
| Project | `overrides/nice-polyglot-config.yml` | Middle (2) | Project maintainer |
| User | `.nice-polyglot/{user}-config.yml` | Highest (3) | Individual contributor |

`{user}` = `git config user.email` sanitized: `@` → `-at-`, `.` → `-`, lowercased.
Fallback to `$env:USERNAME` / `$env:USER` / `unknown` when git email is unavailable.

**Schema** (all fields optional; missing fields fall through to the next lower layer):

```yaml
schema_version: "1.0"       # Optional; reserved for future migration

# Only authoritative at project layer.
# Extension base defines the initial default set.
# User layer MUST NOT set this field (it is ignored if present).
accepted_languages:
  - en                       # Always present
  - fr                       # Example additional language

language_settings:
  interactions: en           # Any language code; unconstrained
  artifacts: en              # Must be in accepted_languages or falls back to en
  documentation: en
  code: en
  code-comments: en
  log-messages: en
  internal-docs: en
  commit-messages: en
```

---

### EffectiveLanguagePolicy

The resolved, validated set of language settings in force for a specific project and user at
runtime. Produced by the merge algorithm from the three `ConfigLayer` instances.

| Attribute | Type | Source |
|---|---|---|
| `accepted_languages` | `LanguageCode[]` | Project layer (authoritative); base layer provides the initial default list; user layer value ignored |
| `interactions` | `LanguageCode` | Highest layer that sets it; unconstrained |
| `artifacts` | `LanguageCode` | Highest layer that sets a valid value; validated against `accepted_languages` |
| `documentation` | `LanguageCode` | Same |
| `code` | `LanguageCode` | Same |
| `code-comments` | `LanguageCode` | Same |
| `log-messages` | `LanguageCode` | Same |
| `internal-docs` | `LanguageCode` | Same |
| `commit-messages` | `LanguageCode` | Same |

---

## Merge Algorithm

Inputs: base `ConfigLayer`, project `ConfigLayer` (optional), user `ConfigLayer` (optional)  
Output: `EffectiveLanguagePolicy`

```
1. Start with base layer values as the working policy.

2. If project layer file exists and is readable:
   a. If accepted_languages is present and non-empty, replace working accepted_languages.
      Always ensure "en" is in the list (add it if absent).
   b. For each language_settings key present in project layer, replace the working value.
   c. If project layer is malformed/unreadable: skip it, retain base values, WARN user.

3. If user layer file exists and is readable:
   a. Ignore any accepted_languages field (FR-010).
   b. For each language_settings key present in user layer, replace the working value.
   c. If user layer is malformed/unreadable: skip it, retain current working values, WARN user.

4. Validate every language_settings value except interactions:
   a. If value is not in accepted_languages → replace with "en", LOG the fallback.

5. Validate interactions:
   a. If value is not a recognized two-letter code → replace with "en", LOG the fallback.
   b. (No accepted_languages constraint for interactions.)

6. If accepted_languages is empty or contains only invalid codes → set to ["en"].

7. Output the working policy as EffectiveLanguagePolicy.
```

---

## Validation Rules

| Rule | Condition | Action |
|---|---|---|
| V-001 | `accepted_languages` is missing or empty | Treat as `[en]` |
| V-002 | `accepted_languages` contains unrecognized codes | Ignore unrecognized codes; retain valid ones; ensure `en` present |
| V-003 | Shared file-output category value not in `accepted_languages` | Fallback to `en`; log the fallback |
| V-004 | `interactions` value is not a two-letter code | Fallback to `en`; log the fallback |
| V-005 | User layer sets `accepted_languages` | Silently ignore (FR-010) |
| V-006 | Any config layer file is malformed or unreadable | Skip that layer; retain values from lower-precedence layers; warn user (FR-011) |
| V-007 | All three config files are missing/unreadable | Use hardcoded defaults: all categories `en`, `accepted_languages: [en]` |

---

## State Transitions

The `EffectiveLanguagePolicy` is stateless — it is re-resolved on every hook invocation from the
current state of the config files. There is no persistent runtime state.

Config file changes take effect the next time a `before_*` hook fires (i.e., the next supported
SpecKit workflow run).

---

## Extension Base Config Defaults

The base `nice-polyglot-config.yml` shipped with the extension defines these defaults:

```yaml
schema_version: "1.0"
accepted_languages:
  - en
language_settings:
  interactions: en
  artifacts: en
  documentation: en
  code: en
  code-comments: en
  log-messages: en
  internal-docs: en
  commit-messages: en
```

All categories default to English. This is the fallback when no project or user config is present.
