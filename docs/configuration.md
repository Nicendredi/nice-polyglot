# Configuration Reference — Nice Polyglot

> **French version**: [docs/configuration.fr.md](configuration.fr.md)

---

## The 8 Language Categories

Nice Polyglot lets you configure the language for each of these output categories
independently:

| Category | What it controls | Constrained by `accepted_languages`? |
|---|---|---|
| `interactions` | Agent-to-user conversational language | **No** — any ISO 639-1 two-letter code |
| `artifacts` | SpecKit artifact files (spec.md, plan.md, tasks.md, …) | Yes |
| `documentation` | User-facing documentation generated by agents | Yes |
| `code` | Generated source code identifiers, strings, and structure | Yes |
| `code-comments` | Comments inside generated source code | Yes |
| `log-messages` | Log output messages generated by agents | Yes |
| `internal-docs` | Internal / developer-facing documentation | Yes |
| `commit-messages` | Git commit messages generated by agents | Yes |

`interactions` is special: it controls the language in which the agent communicates *with
you*. It is the only category that is not constrained by `accepted_languages` — you can
interact in Spanish even if the project only accepts English and French for shared files.

---

## The 3-Layer Precedence Model

Settings are resolved from three optional layers in ascending precedence order:

```
Extension layer (lowest)
      ↓
Project layer
      ↓
User layer (highest)
```

Each layer is optional. When a layer is absent or unreadable the script silently falls
through to the next lower layer. When no layers are present the hardcoded defaults apply
(all categories `en`, `accepted_languages: [en]`).

### Layer File Paths

| Layer | Path (relative to `.specify/` root) | Who creates it |
|---|---|---|
| Extension | `extensions/nice-polyglot/nice-polyglot-config.yml` | SpecKit admin / project team |
| Project | `overrides/nice-polyglot-config.yml` | Project maintainer (commit to project repo) |
| User | `.nice-polyglot/{user}-config.yml` | Individual contributor (do not commit) |

`{user}` is derived at runtime:
1. `git config user.email` — sanitised: `@` → `-at-`, `.` → `-`, lowercased
   (e.g., `alice@example.com` → `alice-at-example-com`)
2. `$env:USERNAME` (Windows) or `$env:USER` (macOS / Linux)
3. Literal `unknown` (warning written to stderr)

## Creating a Project Override

1. Copy `config-template.yml` to `.specify/overrides/nice-polyglot-config.yml`:

   ```bash
   cp config-template.yml .specify/overrides/nice-polyglot-config.yml
   ```

2. Uncomment and set the fields you need:

   ```yaml
   schema_version: "1.0"
   accepted_languages:
     - en
     - fr
   language_settings:
     interactions: fr
     artifacts: fr
     documentation: fr
   ```

3. Commit the file to your project repository so it applies to all contributors.

---

## Creating a User Override

1. Find your expected config path:

   ```powershell
   $email = git config user.email
   $user  = ($email -replace '@', '-at-' -replace '\.', '-').ToLower()
   Write-Host ".specify/.nice-polyglot/$user-config.yml"
   ```

2. Copy `config-template.yml` to that path:

   ```bash
   cp config-template.yml .specify/.nice-polyglot/alice-at-example-com-config.yml
   ```

3. Uncomment and set your personal preferences.

4. **Do not commit** the user config file — it is personal and should be in `.gitignore`.

### User Override Limits

- `accepted_languages` in the user layer is **always ignored** (a warning is written to
  stderr). The project layer is the sole authority for `accepted_languages`.
- All shared file-output categories (`artifacts`, `documentation`, `code`, `code-comments`,
  `log-messages`, `internal-docs`, `commit-messages`) are validated against the project's
  `accepted_languages`. If you set one of these to a language outside the project list the
  **entire user layer is discarded** and a warning is written to stderr.
- `interactions` has no such restriction — you can set it to any valid ISO 639-1 two-letter
  code regardless of `accepted_languages`.

---

## `accepted_languages` Behaviour

`accepted_languages` declares the set of languages that are valid for shared file-output
categories. Rules:

- Each value must be an ISO 639-1 two-letter lowercase code (e.g. `en`, `fr`, `es`).
- `en` is always implicitly present. If you omit it, it is added automatically.
- If any code in the list is invalid (does not match `/^[a-z]{2}$/`) the **entire layer is
  discarded** (V-002).
- An empty or missing `accepted_languages` is treated as `[en]` (V-001).
- Only the **project layer** is authoritative for `accepted_languages`. The extension layer
  may set it as a shared default; the user layer value is ignored.

## Annotated Example

This example mirrors the scenario in the developer quickstart guide.

### Base state (no config files)

Running the script with no config files produces all-English defaults:

```
NICE_POLYGLOT_POLICY_START
accepted_languages: en
interactions: en
artifacts: en
documentation: en
code: en
code-comments: en
log-messages: en
internal-docs: en
commit-messages: en
NICE_POLYGLOT_POLICY_END
```

### After adding a project override

**File**: `.specify/overrides/nice-polyglot-config.yml`

```yaml
schema_version: "1.0"
accepted_languages:
  - en
  - fr
language_settings:
  interactions: fr
  artifacts: fr
  documentation: fr
```

Running the script now produces:

```
NICE_POLYGLOT_POLICY_START
accepted_languages: en,fr
interactions: fr
artifacts: fr
documentation: fr
code: en
code-comments: en
log-messages: en
internal-docs: en
commit-messages: en
NICE_POLYGLOT_POLICY_END
```

*`code`, `code-comments`, `log-messages`, `internal-docs`, `commit-messages` remain `en`
because the project override did not set them.*

### After adding a user override

**File**: `.specify/.nice-polyglot/alice-at-example-com-config.yml`

```yaml
schema_version: "1.0"
language_settings:
  interactions: es
```

Running the script now produces:

```
NICE_POLYGLOT_POLICY_START
accepted_languages: en,fr
interactions: es
artifacts: fr
documentation: fr
code: en
code-comments: en
log-messages: en
internal-docs: en
commit-messages: en
NICE_POLYGLOT_POLICY_END
```

*`interactions` is `es` (Spanish) because it is unconstrained by `accepted_languages`.*
*`accepted_languages` stays `en,fr` from the project layer — the user cannot change it.*
*All shared file-output categories are still validated against `[en, fr]`.*

## Validation at a Glance

| Scenario | Result |
|---|---|
| Layer file absent | Layer skipped silently |
| Layer file unreadable / malformed | Layer skipped; warning on stderr |
| `accepted_languages` contains invalid code | Entire layer discarded; warning on stderr |
| Shared category set to code outside `accepted_languages` | Entire layer discarded; warning on stderr |
| `interactions` set to invalid code | Entire layer discarded; warning on stderr |
| User layer sets `accepted_languages` | Field ignored; warning on stderr; rest of user layer applied if valid |
| `accepted_languages` empty after merge | Treated as `[en]` |
